# Что делать, если журнал взломали

Этот файл читают в плохой день, поэтому здесь только порядок действий и
команды. Разбираться, как так вышло, будем потом — сначала останавливаем.

Как всё устроено (проверено 30.09.2026):

| Что | Где |
|---|---|
| Сервер | Hetzner, `root@94.130.58.113`, Ubuntu 24.04 |
| Код | `/opt/trading-journal`, служба `trading-journal` под пользователем `journal` |
| Сам журнал | слушает только `127.0.0.1:8172` — снаружи не достучаться |
| Впереди | Caddy: он держит 80 и 443 и весь HTTPS |
| База | **своя, на этой же машине**, `127.0.0.1:5433` |
| Наружу открыто | только 22, 80, 443 (ufw) |
| Доступы | `/opt/trading-journal/.env`, права `600 journal` |

То, что база своя, а не в облаке, меняет главное: **никто, кроме нас, её
не бэкапит**. Смотри раздел 5.

---

## 1. Понять, что вообще происходит

След безопасности пишется в журнал службы. Смотреть так:

```bash
ssh root@94.130.58.113
journalctl -u trading-journal -n 500 | grep statsai-sec       # входы, пароли, 2FA, админка
journalctl -u trading-journal | grep "statsai-sec.*ЗБІЙ"      # только неудачи
journalctl -u trading-journal | grep "підбір пароля"          # перебор пароля
journalctl -u trading-journal -p err -n 200                   # ошибки и падения
```

Что тревожно:

- десятки `вхід ЗБІЙ` с одного `ip=` — перебор; журнал сам замедляет такого,
  но посмотреть, добрался ли он до чьего-то аккаунта, стоит;
- `вхід ok` с незнакомого адреса под твоим `uid`;
- `адмінка ЗБІЙ` — кто-то ломился в служебную панель;
- `2fa ... стан=вимкнено` или `пароль ... як=скидання`, которых ты не делал;
- `адмін ... дія=видалення` не от тебя.

## 2. Остановить, если атака идёт прямо сейчас

```bash
systemctl stop trading-journal        # сайт ложится целиком, зато ничего не пишется
```

Это грубо, но честно: пока не понял, что происходит, пусть лучше сайт
полежит десять минут. Если атака точечная — по одному адресу:

```bash
ufw deny from АДРЕС
```

База снаружи и так недоступна: она слушает только `127.0.0.1`. Но если
подозрение, что залезли на саму машину, — **первым делом снять снимок
базы**, пока её не испортили:

```bash
/usr/local/bin/tj-dump
```

И сразу забрать файл к себе, со своей машины:

```bash
scp -i ~/.ssh/id_ed25519_hetzner root@94.130.58.113:/var/backups/statsai/*.sql.gz .
```

## 3. Выбить всех из журнала

Смена ключа подписи выбрасывает **все** сессии разом: чужая украденная кука
перестаёт работать в ту же секунду.

```bash
nano /opt/trading-journal/.env        # SESSION_SECRET — новая длинная случайная строка
systemctl restart trading-journal
```

Новую строку взять так: `openssl rand -hex 32`.

Если ключ лежит не в `.env`, а в базе (так бывает, когда переменную не
задавали), — удалить строку `session_secret` из таблицы `meta`, журнал
заведёт новый сам.

## 4. Сменить ключи

Все живут в `/opt/trading-journal/.env`. После правки —
`systemctl restart trading-journal`. Менять в таком порядке:

| Ключ | Где меняется | Что будет, если не сменить |
|---|---|---|
| `SESSION_SECRET` | сам придумываешь | чужой вход остаётся действующим |
| `DATABASE_URL` | `ALTER ROLE ... PASSWORD '...'` в своём Postgres (порт 5433), потом строка в `.env` | доступ ко всем данным журнала |
| `BOT_TOKEN` | @BotFather → `/revoke` | чужой пишет от имени бота |
| `SMTP_PASS` | почтовый ящик, пароль приложения | рассылка писем от нашего адреса |
| `CREEM_API_KEY`, `CREEM_WEBHOOK_SECRET` | кабинет Creem | подделка оплат |
| `DEEPSEEK_API_KEY` | кабинет DeepSeek | счёт за чужие запросы |
| `GOOGLE_CLIENT_SECRET`, `DISCORD_CLIENT_SECRET` | консоли Google / Discord | вход под чужим аккаунтом |
| `TRON_KEY`, `OANDA_TOKEN` | TronGrid / OANDA | счёт за чужие запросы |
| ssh-ключ | `~/.ssh/authorized_keys` на сервере | доступ к самому серверу |

Важно: ключ, который **мог** утечь, считается утёкшим. Проверять
«а точно ли» — потом.

## 5. Вернуть данные

Порядок от лёгкого к тяжёлому:

1. **Слепок одного журнала** — `backup.py` каждый день кладёт слепок по
   каждому человеку прямо в базу, хранит 14 дней. Достать: таблица
   `backups`, или через сайт кнопкой «Скачать журнал». Это лечит «человек
   снёс свои сделки» и не лечит ничего больше: слепки лежат в той же базе,
   что и данные.
2. **Снимок всей базы файлом** — `tools/pgdump.sh` (на сервере
   `/usr/local/bin/tj-dump`), снимки в `/var/backups/statsai/`, держим 14
   штук. Вернуть целиком:

   ```bash
   systemctl stop trading-journal
   gunzip -c /var/backups/statsai/statsai-ДАТА.sql.gz | psql "$DATABASE_URL"
   systemctl start trading-journal
   ```

   Чтобы не затирать живое поверх, безопаснее развернуть снимок в новую базу
   и посмотреть, то ли это, а уже потом переключать `DATABASE_URL`.
3. **Код** — `./deploy.sh` выкладывает `origin/main` заново. Если подменили
   файлы на сервере, это лечится одной командой.

**Копия обязана лежать не здесь.** Снимок на том же диске не спасает от
смерти диска и от того, кто добрался до сервера. Забирать к себе — со своей
машины (не с сервера: у сервера не должно быть доступа в хранилище):

```bash
scp -i ~/.ssh/id_ed25519_hetzner \
    root@94.130.58.113:/var/backups/statsai/*.sql.gz ~/backups/statsai/
```

### Поставить снимки по расписанию

```bash
cp /opt/trading-journal/tools/pgdump.sh /usr/local/bin/tj-dump
chmod +x /usr/local/bin/tj-dump
/usr/local/bin/tj-dump                      # проверить руками

cat > /etc/systemd/system/tj-dump.service <<'EOF'
[Unit]
Description=Снимок базы журнала
[Service]
Type=oneshot
ExecStart=/usr/local/bin/tj-dump
EOF

cat > /etc/systemd/system/tj-dump.timer <<'EOF'
[Unit]
Description=Снимок базы журнала раз в сутки
[Timer]
OnCalendar=*-*-* 03:30:00
Persistent=true
[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload
systemctl enable --now tj-dump.timer
systemctl list-timers tj-dump.timer --no-pager     # когда сработает
```

Раз в месяц снимок надо **проверять**: развернуть в отдельную базу и
посмотреть, что данные на месте. Непроверенная копия — не копия.

## 6. Кого предупредить

- **Владельца** (если ты не он) — сразу, любым способом.
- **Людей в журнале** — если их данные могли уйти. Что писать: что
  случилось, какие данные затронуты, что сделать им (сменить пароль,
  включить 2FA). Врать про «инцидент с инфраструктурой» не надо.
- **Партнёров** (FX LAB, Black Swan) — если ломали через их ссылки или
  пострадали их люди.
- **Хостинг** (Hetzner) — если сервер используют для атак на других:
  иначе его отключат без разговоров.

## 7. Чего ждать письмом

Взлом чаще начинается не с кода, а с письма. Настораживать должно:

- письмо «от Hetzner / Creem / GitHub / DeepSeek» с просьбой войти по ссылке —
  адрес набирать руками, по ссылке из письма не ходить никогда;
- «подтвердите вход» или код 2FA, которого ты не запрашивал — значит,
  пароль уже у кого-то есть, и надо менять его, а не вводить код;
- письмо от «пользователя журнала» с вложением или ссылкой на «скриншот
  ошибки»;
- просьба «срочно, пока владелец недоступен» — спешка и есть приём.

Пароль и код из приложения не спрашивает никто. Ни бот, ни поддержка,
ни я.

## Что уже сделано в коде

Чтобы не искать по репозиторию:

- запросы к базе — только параметрами, сторож `test_sql_safe.py`;
- вывод экранируется, стоит `Content-Security-Policy`;
- пароли — PBKDF2-HMAC-SHA256, 200 000 повторов, сравнение стойкое к времени;
- сессия — подписанная HttpOnly-кука с «поколением»: смена пароля гасит все входы;
- 2FA, запасные коды хранятся хешами;
- перебор пароля упирается в растущие паузы, владельцу уходит письмо;
- общий потолок на запросы с одного адреса (`ratelimit.flood`);
- загружаемые файлы проверяются по первым байтам, имя даём своё;
- служебные адреса закрыты, за этим следит `test_privileges.py`.

Чего в коде нет и быть не может: фильтрации трафика и CDN перед сайтом.
Домен смотрит прямо на сервер, поэтому объёмная атака кодом не лечится —
нужен Cloudflare. Перед его включением журнал должен научиться читать
`CF-Connecting-IP`, иначе все посетители станут одним адресом и упрутся в
общий потолок.

## Что проверять раз в месяц

- `apt list --upgradable` — и обновиться, если ждут security-обновления;
- `systemctl list-timers tj-dump.timer` — снимки базы делаются;
- развернуть последний снимок в отдельную базу и убедиться, что он живой;
- `journalctl -u trading-journal | grep "statsai-sec.*ЗБІЙ" | tail -50` —
  не ломился ли кто-то в чужие аккаунты;
- `ufw status` — наружу по-прежнему открыты только 22, 80, 443.
